# 문제 1. 테스트 자동화 전략 설계

## 전제

- "실시간 주문 현황"은 고객이 주문 후 상태 변화(주문접수 → 조리중 → 배달중 → 배달완료, 취소)를 실시간으로 확인하는 화면으로 가정합니다.
- 상태 변경은 서버 이벤트(SSE/WebSocket 등)로 전달되고, 연결이 끊기면 재조회로 보정하는 구조로 가정합니다.
- 개발 2주, 개발자 2명, 기존 자동화 없음. 오픈 전까지 화면은 계속 바뀔 수 있다고 봅니다.

---

## 1-1. 자동화 전략 수립

### 판단 기준

자동화 여부는 아래 네 가지로 판단합니다.

| 기준 | 자동화 | 수동 |
|---|---|---|
| 반복 빈도 | 매 배포·회귀마다 반복 | 1~2회 확인하면 끝 |
| 스펙 안정도 | 정책이 확정되어 잘 안 바뀜 | 기획·UI가 아직 바뀌는 중 |
| 장애 영향 | 깨지면 주문·CS로 바로 이어짐 | 영향이 제한적 |
| 판정 방식 | 값·상태·응답코드로 판정 가능 | 사람의 눈과 체감이 필요 |

### 자동화 / 수동 범위

| 구분 | 대상 |
|---|---|
| 자동화 | 주문 상태 조회 API 응답 검증 |
| 자동화 | 상태 전이 규칙 (정상 전이, 허용되지 않는 전이 거부, 취소 시 처리) |
| 자동화 | 상태 변경 이벤트 수신 후 최신 상태 반영 (이벤트 누락·순서 뒤바뀜 시 재조회 보정 포함) |
| 자동화 | 핵심 E2E 1~2개 (주문 → 상태 변경 → 화면 반영) |
| 수동 | 실시간 갱신 체감, 애니메이션, 화면 전환 자연스러움 |
| 수동 | 지도·라이더 위치 표시, 다양한 기기·OS 레이아웃 |
| 수동 | 백그라운드 전환, 네트워크 끊김 등 예외 상황 탐색적 테스트 |

### 레이어별 배분 (테스트 피라미드)

| 레이어 | 비중 | 내용 | 이유 |
|---|---|---|---|
| API / 계약 | 약 70% | 상태 조회, 전이 규칙, 이벤트 페이로드 | 빠르고 안정적. 스펙 확정 즉시 스텁 기반으로 시작 가능 |
| UI 컴포넌트 | 약 20% | 상태별 화면 렌더링 (개발과 분담) | 상태 값에 따른 표시만 검증, 서버 의존 제거 |
| E2E | 약 10% | 핵심 해피패스 1~2개 | 신뢰도는 높지만 느리고 불안정할 수 있어 최소화 |

### 2주 일정 배분

- **1주차:** 기획 리뷰에서 상태 정의와 전이 규칙 확정 → API 명세 기준 스텁으로 API 테스트 작성. 개발과 동시에 진행합니다.
- **2주차:** 실제 API 연결 후 API 테스트 전환, 핵심 E2E 1~2개 작성, 나머지는 수동 테스트로 검증.
- **오픈 이후:** 화면이 안정되면 회귀에서 반복 확인하는 UI 케이스를 자동화로 옮깁니다.

### ROI 판단

비용은 작성 비용만이 아니라 **유지보수 비용과 Flaky 대응 비용**까지 포함해서 봅니다. 효과는 절감되는 수동 테스트 시간, 결함 조기 발견, 주문 장애 리스크 감소로 봅니다.

- 예: 수동 30분 TC를 자동화하는 데 8시간, 이후 회당 유지보수 5분이 든다면 회당 25분 절감 → **약 20회 이상 실행되어야 이득**입니다. 그래서 매 배포 회귀에 들어가는 케이스부터 자동화합니다.
- 오픈 전 UI 자동화는 화면 변경 때마다 수정 비용이 생겨 ROI가 낮다고 판단해 미룹니다.
- 도입 후에는 **회귀 소요 시간, 자동화로 사전 발견한 결함 수, Flaky 비율, 유지보수 시간**을 기록하고, 분기마다 유지비가 효과를 넘는 테스트는 정리합니다.

## 1-2. 파이프라인 통합

### 단계별 실행

| 단계 | 실행 테스트 | 목표 시간 | 실패 시 |
|---|---|---|---|
| PR 생성 | API 테스트(스텁), UI 컴포넌트 테스트 | 10분 이내 | merge 차단 |
| merge 후 dev 배포 | API 통합 테스트 (실제 서버) | 20분 이내 | 담당자 알림, 다음 배포 보류 |
| Nightly | E2E 전체 + 회귀 | 제한 없음 | 다음 날 오전 결과 리뷰 |
| 스테이징 배포 | Smoke (핵심 경로) | 10분 이내 | 운영 배포 차단 |
| 운영 배포 직후 | Smoke (조회 위주, 실주문 영향 없는 범위) | 5분 이내 | 롤백 판단 |

PR 단계에는 빠르고 안정적인 테스트만 둡니다. 느리거나 외부 의존이 큰 테스트는 Nightly로 보내 개발 흐름을 막지 않게 합니다.

### Flaky 테스트 대응 정책

1. **탐지:** 테스트별 실행 이력을 남기고, 같은 커밋에서 결과가 달라지면 Flaky 후보로 표시합니다.
2. **재시도:** 자동 재시도는 1회만 허용합니다. 재시도로 통과해도 "Flaky 발생"으로 기록해서 재시도가 문제를 가리지 않게 합니다.
3. **격리:** 최근 실행 기준 실패율이 기준(예: 2%)을 넘으면 격리합니다. 배포 게이트에서는 제외하지만 실행은 계속해서 이력을 쌓습니다.
4. **원인 분석:** 격리와 동시에 담당자를 지정하고 기한(예: 1주)을 둡니다. 원인은 대기·타이밍 / 테스트 데이터 / 환경 / 셀렉터 / 실제 버그로 분류합니다.
5. **복귀:** 수정 후 연속 N회(예: 20회) 통과하면 게이트에 다시 포함합니다. 기한 내 수정이 어려우면 삭제하거나 수동으로 전환합니다.

실제 버그가 간헐적으로 드러나는 경우(예: 이벤트 순서가 가끔 뒤바뀜)도 있으므로, Flaky를 무조건 테스트 문제로 보지 않고 제품 결함 가능성을 먼저 확인합니다.

---

## 경험에서 가져온 점

실 단위로 도메인별 Smoke TC 자동화를 구축해 핵심 경로를 검증했습니다. 대상을 자주 바뀌지 않는 핵심 경로로 좁혀서 결과가 불안정한 경우는 거의 없었습니다. 범위를 좁게 잡는 판단이 안정성으로 이어진다는 점을 이번 전략에도 반영했습니다.

다만 필요할 때 담당자가 직접 실행하는 방식이라, 바쁜 배포 주간에는 실행이 빠질 수 있다는 한계가 있었습니다. 이번 설계에서는 Smoke를 배포 단계에 고정해 사람의 판단 없이 항상 실행되도록 했습니다.
