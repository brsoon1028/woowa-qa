## 문제 1. 테스트 자동화 전략 설계

### 실행 방법

서술형 문항이라 실행할 코드는 없습니다. [문제1/strategy.md](./문제1/strategy.md)에서 확인할 수 있습니다.

### 설계 의도

- **판단 기준을 먼저 세웠습니다.** 반복 빈도, 스펙 안정도, 장애 영향, 판정 방식의 4가지 기준으로 자동화 대상을 고르고, 같은 기준으로 수동 영역을 남겼습니다.
- **API 중심의 피라미드로 배분했습니다.** 개발 기간이 2주이고 화면이 계속 바뀔 수 있어서, 스펙이 먼저 확정되는 API·상태 전이 규칙을 두껍게 두고 E2E는 핵심 흐름 1~2개로 제한했습니다.
- **ROI에 유지보수 비용과 Flaky 비용을 포함했습니다.** 작성 비용만 보면 UI 자동화가 매력적으로 보이지만, 오픈 전 화면 변경에 따른 수정 비용을 고려해 오픈 이후로 미뤘습니다.
- **Flaky는 재시도로 덮지 않습니다.** 재시도로 통과해도 기록하고, 기준을 넘으면 격리하되 실행은 계속해서 원인을 찾는 구조로 설계했습니다.
- **기존 경험의 한계를 반영했습니다.** 실무에서 운영한 Smoke 자동화는 담당자가 필요할 때 실행하는 방식이라 실행이 빠질 수 있었습니다. 이번 설계에서는 Smoke를 배포 단계에 고정했습니다.

### 가정

- "실시간 주문 현황"은 고객이 주문 상태 변화를 실시간으로 확인하는 화면이며, 서버 이벤트(SSE/WebSocket 등)로 갱신된다고 가정했습니다.
- 레이어별 비중(70/20/10), Flaky 격리 기준(2%), 복귀 조건(연속 20회 통과)은 판단 기준을 보여주기 위한 예시 값입니다.

## 문제 2. B마트 재고 API 테스트 자동화

### 실행 방법

Python 3.11 이상이 필요합니다.

```bash
cd 문제2
pip install -r requirements.txt
pytest -v
```

- 스텁 서버는 테스트가 실행될 때 자동으로 기동되고 종료됩니다. 별도로 서버를 띄울 필요가 없습니다.
- 전체 실행 시간은 약 35초입니다. 대부분 동시성 시나리오 50회 반복에 쓰입니다.
- 동시성 테스트만 실행: `pytest tests/test_concurrency.py -v`
- 버그 모드 확인만 실행: `pytest -m bugmode -v`

### 구성

| 파일 | 역할 |
|---|---|
| [API_SPEC.md](./문제2/API_SPEC.md) | 가상 API 명세와 정책 정의 |
| [TEST_CASES.md](./문제2/TEST_CASES.md) | 테스트 케이스 13건과 제외 케이스 |
| `stub_server/app.py` | 명세대로 재고를 차감·복구하는 스텁 서버 |
| `tests/conftest.py` | fixture: 테스트별 서버 기동, 사전조건 데이터 세팅 |
| `tests/helpers.py` | 공통 설정값, 데이터 세팅·후속 검증 헬퍼 |
| `tests/api_client.py` | API 호출 래퍼 |
| `tests/test_*.py` | TC별 테스트 (함수 이름에 TC 번호 표기) |

### 설계 의도

- **정적 Mock 대신 상태를 가진 스텁 서버를 직접 구현했습니다.** 응답을 미리 고정하는 Mock으로는 "두 요청 중 하나만 성공"이 서버 로직의 결과인지 검증할 수 없습니다. 스텁은 메모리에 재고를 두고 실제로 차감·복구하며, 재고 확인과 차감을 하나의 잠금 구간에서 처리합니다.
- **테스트가 버그를 잡을 수 있는지까지 확인했습니다.** 잠금을 끈 버그 모드 서버를 함께 두고, 같은 시나리오에서 초과 판매가 재현되는지 확인하는 테스트(`-m bugmode`)를 포함했습니다. 버그 모드에서 TC-12의 검증 조건은 20회 중 20회 모두 실패했습니다.
- **동시성은 반복 실행으로 신뢰도를 확보했습니다.** 경합은 타이밍에 따라 드러나지 않을 수 있어 TC-12를 50회 반복합니다. 반복 횟수와 요청 간격은 `tests/helpers.py`의 설정값으로 조정할 수 있습니다.
- **테스트 간 데이터가 섞이지 않게 했습니다.** 테스트마다 새 스텁 서버를 띄우고 종료합니다.

### 테스트 코드 구조

- **fixture (`conftest.py`):** `server_factory`가 옵션(잠금 사용 여부, 처리 지연)을 바꿔 서버를 띄우고, `api`가 기본 서버의 클라이언트를, `product(n)`이 "재고 n개 상품" 사전조건을 만듭니다.
- **데이터 준비:** 사전조건은 운영자 재고 수정 API로 세팅합니다. 테스트 코드가 서버 내부를 직접 바꾸지 않고 API만으로 상태를 만듭니다.
- **검증 헬퍼:** `assert_stock()`이 TC의 "후속 검증"을 담당해 재고 조회 API로 수량과 상태를 확인합니다. 실패하면 기대값과 실제값을 함께 출력합니다.
- **API 래퍼:** 테스트는 URL을 직접 쓰지 않고 `StockApiClient`의 메서드만 호출합니다. 경로가 바뀌어도 한 파일만 고치면 됩니다.
- **TC 추적:** 함수 이름에 TC 번호를 붙여(`test_tc07_...`) TEST_CASES.md와 바로 대응되게 했습니다.

### 가정

- 정책 판단(재고 초과 주문 전량 거부, 중복 취소 에러 응답, 운영자 수정 API 추가, 동시 요청은 도착 순서대로 처리)은 [API_SPEC.md](./문제2/API_SPEC.md)에 정의했습니다.
- 스텁 서버의 처리 지연(50ms)은 실제 서버의 결제·DB 처리 시간을 흉내 내기 위한 값으로, 수십 ms 간격으로 도착한 두 요청의 처리가 겹치도록 요청 간격(20ms)보다 길게 잡았습니다.
- "생성된 주문 수"는 스텁 서버 내부 저장소로 확인합니다. 주문 목록 조회 API가 과제에 없기 때문입니다.

## 문제 3. E2E 자동화 코드 리뷰 및 리팩토링

### 실행 방법

과제 안내에 따라 실행 환경 없이 설계 의도를 보여주는 코드로 작성했습니다. 앱 패키지명, resource-id, 테스트용 API는 예시 값입니다.

- 문제점 분석, 개선 내용, Flaky 추적 순서: [문제3/review.md](./문제3/review.md)
- 리팩토링 코드: [문제3/src](./문제3/src)

### 설계 의도

- **문제점을 안정성, 신뢰성, 유지보수성으로 나눠 핵심 8가지로 정리했습니다.** 특히 "통과해도 믿을 수 없는 문제"(신뢰성)를 따로 분리했습니다. 원본은 화면 어딘가에 "접수 대기" 문구만 있으면 통과하기 때문입니다.
- **Page Object로 화면 조작과 검증을 분리했습니다.** 테스트 본문에는 무엇을 검증하는지만 남기고, 화면이 바뀌면 해당 Page 파일만 고치도록 했습니다.
- **고정 대기를 조건 기반 대기로 바꿨습니다.** `Thread.sleep(5000)` 대신 결제 처리 화면이 사라지고 주문 현황이 뜰 때까지 기다립니다. 타임아웃은 한곳에서 관리하고 CI에서 배율로 조정합니다.
- **요소를 못 찾으면 원인을 남기고 실패합니다.** null 클릭으로 인한 NPE 대신 "어느 화면, 어떤 요소"를 메시지로 남기고, 실패 시 스크린샷과 UI 덤프를 저장합니다. Flaky 추적의 첫 단계가 이 정보이기 때문입니다.
- **사전조건과 정리는 API로 처리합니다.** 로그인, 배송지, 장바구니, 가게 영업 상태를 테스트 전에 맞추고, 생성된 주문은 테스트 후 취소합니다.
- **일시적인 상태를 고정값으로 검증하지 않습니다.** 주문 직후 허용되는 상태 집합(접수 대기, 접수 완료)으로 검증하고, 자동 접수를 끈 테스트 가게를 사용합니다.

## 문제 4. AI 활용 QA 도구 제안

### 실행 방법

설계 문서와 프롬프트 설계로 제출했습니다.

- 도구 설계: [문제4/design.md](./문제4/design.md)
- 단계별 프롬프트: [문제4/prompts](./문제4/prompts)

### 설계 의도

- **TC 생성기가 아니라 기획 리뷰 보조 도구로 설계했습니다.** 기획서로 TC를 생성하는 도구는 대부분 기획서가 완성돼 있다고 가정합니다. 실무에서 겪은 운영 이슈는 TC를 잘못 만든 것이 아니라 기획서에 없던 정책 때문이었기에, 기획 리뷰 전에 정책 공백을 찾는 것을 핵심 결과물로 두고 TC 초안은 그 다음 단계로 두었습니다.
- **공백 탐지 관점을 고정했습니다.** 경계값, 상태 전이, 동시 발생, 실패·취소, 권한·주체, 영향범위 6가지를 요구사항마다 대입하게 해 결과 품질을 일정하게 유지합니다.
- **AI 출력을 검증하는 단계를 따로 두었습니다.** 모든 요구사항과 TC에 원문 인용과 요구사항 ID를 강제하고, 누락·근거 없음·양식 위반은 규칙으로, 내용 불일치만 검토 프롬프트로 확인합니다.
- **도구 자체를 테스트 대상으로 봤습니다.** 문제 2에서 직접 찾은 정책 공백 4가지와 과거에 놓친 사례를 정답셋으로 삼아, 도구를 바꿀 때마다 공백을 몇 개 찾아내는지 회귀 검증합니다. 문제 2에서 버그 모드로 테스트가 버그를 잡는지 확인한 것과 같은 접근입니다.
