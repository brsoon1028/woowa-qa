# B마트 재고 API 명세 (테스트용 가정)

실제 서버가 없으므로 과제 요구사항을 바탕으로 정의한 명세입니다. 테스트와 스텁 서버는 이 명세를 기준으로 동작합니다.

## 공통

- 요청·응답 형식: JSON
- 에러 응답 형식: `{"code": "<에러코드>", "message": "<설명>"}`
- 재고 상태: `AVAILABLE` (재고 1개 이상), `SOLD_OUT` (재고 0)

## 1. 재고 조회

`GET /v1/products/{productId}/stock`

| 결과 | 상태코드 | 응답 |
|---|---|---|
| 성공 | 200 | `{"productId": "P001", "quantity": 5, "status": "AVAILABLE"}` |
| 없는 상품 | 404 | `PRODUCT_NOT_FOUND` |

- 장바구니 담기는 재고 조회만 하며 재고를 차감하지 않습니다.

## 2. 주문 생성 (재고 차감)

`POST /v1/orders`

요청: `{"productId": "P001", "quantity": 1, "customerId": "C001"}`

| 결과 | 상태코드 | 응답 |
|---|---|---|
| 성공 | 201 | `{"orderId": "O001", "productId": "P001", "quantity": 1, "status": "PAID"}` |
| 수량이 0 이하 또는 정수가 아님 | 400 | `INVALID_QUANTITY` |
| 없는 상품 | 404 | `PRODUCT_NOT_FOUND` |
| 재고 부족 또는 품절 | 409 | `OUT_OF_STOCK` |

- 결제 완료 시점에 주문 수량만큼 즉시 차감합니다.
- **재고보다 많은 수량을 주문하면 전량 거부합니다.** 부분 주문은 만들지 않으며 재고는 변하지 않습니다.
- 차감 후 재고가 0이 되면 즉시 `SOLD_OUT`으로 전환합니다.
- **동시 주문은 서버 도착 순서(선착순)로 처리**하며, 재고를 넘는 이후 요청은 `OUT_OF_STOCK`으로 응답합니다.

## 3. 주문 취소 (재고 복구)

`POST /v1/orders/{orderId}/cancel`

| 결과 | 상태코드 | 응답 |
|---|---|---|
| 성공 | 200 | `{"orderId": "O001", "status": "CANCELLED"}` |
| 없는 주문 | 404 | `ORDER_NOT_FOUND` |
| 이미 취소된 주문 | 409 | `ALREADY_CANCELLED` |

- 취소 즉시 주문 수량만큼 재고를 복구하고, `SOLD_OUT` 상태였다면 `AVAILABLE`로 전환합니다.
- **이미 취소된 주문은 에러로 응답하며 재고를 다시 복구하지 않습니다.**

## 4. 운영자 재고 수정 (추가 정의)

`PUT /v1/admin/products/{productId}/stock`

요청: `{"quantity": 10}`

| 결과 | 상태코드 | 응답 |
|---|---|---|
| 성공 | 200 | `{"productId": "P001", "quantity": 10, "status": "AVAILABLE"}` |
| 수량이 음수 또는 정수가 아님 | 400 | `INVALID_QUANTITY` |
| 없는 상품 | 404 | `PRODUCT_NOT_FOUND` |

- 과제의 "운영자가 재고 수동 수정" 규칙을 검증하기 위해 추가한 API입니다.
- 입력값으로 재고를 즉시 덮어쓰며, 0이면 `SOLD_OUT`, 1 이상이면 `AVAILABLE`로 전환합니다.
- **수정과 주문이 동시에 들어오면 서버에 먼저 도착한 요청부터 처리합니다.** 동시 주문의 선착순 규칙과 같은 기준입니다.

## 범위 밖

- "다른 탭에서 조회 중인 고객에게 품절 즉시 반영"은 화면·실시간 갱신 영역이라 API 테스트 범위에서 제외합니다. API에서는 품절 전환 직후 재고 조회가 `SOLD_OUT`을 반환하는지까지 검증합니다.
- 결제 승인 자체(PG 연동)는 범위 밖이며, 주문 생성 성공을 결제 완료로 간주합니다.
