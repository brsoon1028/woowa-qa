# 문제 3. E2E 자동화 코드 리뷰 및 리팩토링

## 원본 코드

```kotlin
@Test
fun testOrderFlow() {
    val shopItem = device.wait(Until.findObject(By.textContains("치킨")), 5000)      // L1
    shopItem.click()                                                                // L2
    val menuItem = device.wait(Until.findObject(By.textContains("후라이드")), 3000)   // L3
    menuItem.click()                                                                // L4
    val orderBtn = device.wait(Until.findObject(By.textContains("주문하기")), 3000)   // L5
    orderBtn.click()                                                                // L6
    val payBtn = device.wait(Until.findObject(By.textContains("결제")), 3000)         // L7
    payBtn.click()                                                                  // L8
    Thread.sleep(5000)                                                              // L9
    val statusText = device.wait(Until.findObject(By.textContains("접수 대기")), 3000) // L10
    Assert.assertNotNull(statusText)                                                // L11
}
```

---

## 1. 운영 환경에서 발생할 수 있는 문제점

### 안정성: 실행할 때마다 결과가 달라질 수 있음

**① 요소를 못 찾으면 원인 모를 에러로 멈춤 (L1~L8)**
`device.wait()`는 요소를 못 찾으면 `null`을 돌려주는데, 확인 없이 바로 `click()`을 호출합니다. 화면 로딩이 조금만 늦어도 `NullPointerException`이 나고, 로그만으로는 어느 단계에서 무엇을 못 찾았는지 알 수 없습니다.

**② 고정 시간 대기 (L9, 타임아웃 값 전체)**
`Thread.sleep(5000)`은 결제가 5초보다 오래 걸리면 실패하고, 빠르면 매번 시간을 낭비합니다. 단계별 타임아웃(5000, 3000)도 하드코딩되어 있어, 로컬보다 느린 CI 에뮬레이터에서 간헐적으로 실패하기 쉽습니다.

**③ 금방 바뀌는 상태를 고정값으로 검증 (L10)**
"접수 대기"는 사장님이 주문을 접수하면 바로 바뀌는 일시적인 상태입니다. 5초 대기 중에 상태가 바뀌면 실패하므로, 테스트 결과가 사장님 쪽 동작에 좌우됩니다.

### 신뢰성: 통과해도 믿을 수 없음

**④ 화면 문구로 요소를 찾음 (L1, L7)**
`textContains("치킨")`은 카테고리, 광고 배너, 가게명에 모두 걸리고, `textContains("결제")`는 "결제수단", "결제 금액"에도 걸립니다. 엉뚱한 요소를 누르고도 우연히 진행될 수 있고, 문구가 하나만 바뀌어도 테스트가 깨집니다.

**⑤ 검증이 너무 약함 (L11)**
`assertNotNull` 하나만 있어서 화면 어딘가에 "접수 대기" 문구만 있으면 통과합니다. 주문한 가게, 메뉴, 금액, 주문번호를 확인하지 않아 잘못된 주문이 만들어져도 알 수 없습니다.

**⑥ 사전조건과 테스트 데이터를 관리하지 않음 (전체)**
로그인, 배송지, 장바구니, 가게 영업 상태를 보장하지 않아 이전 테스트가 남긴 상태에 따라 결과가 달라집니다. 테스트 결제수단 사용 여부도 드러나지 않고, 만들어진 주문을 정리하지 않아 테스트 주문이 계속 쌓입니다.

### 유지보수성: 고치기 어려움

**⑦ 화면 조작과 검증이 한 함수에 섞여 있음 (전체)**
주문 화면이 바뀌면 이 흐름을 쓰는 모든 테스트를 각각 고쳐야 합니다. 함수명 `testOrderFlow`도 무엇을 검증하는지 드러내지 않습니다.

**⑧ 실패했을 때 남는 정보가 없음 (전체)**
스크린샷이나 화면 구조를 저장하지 않아, CI에서 실패하면 원인을 보려고 재현부터 다시 해야 합니다. Flaky 테스트를 추적하기 가장 어려운 이유가 됩니다.

## 2. 리팩토링

코드는 [src/](./src) 폴더에 있습니다. 실행 환경이 없으므로 설계 의도를 보여주는 형태로 작성했습니다.

### 구조

```
src/
├── OrderFlowTest.kt          ← 테스트 본문 (무엇을 검증하는지만 보임)
├── base/
│   ├── BaseUiTest.kt         ← 공통 준비: 기기, 앱 실행, 팝업 처리
│   └── FailureCaptureRule.kt ← 실패 시 스크린샷·UI 덤프 저장
├── pages/                    ← Page Object (화면별 조작)
│   ├── HomePage.kt
│   ├── StorePage.kt
│   ├── CartPage.kt
│   ├── CheckoutPage.kt
│   └── OrderStatusPage.kt
├── support/
│   ├── Ui.kt                 ← 대기·검색 헬퍼, 타임아웃 설정
│   └── TestOrderApi.kt       ← 사전조건 세팅·정리용 테스트 API (가정)
└── data/
    └── TestData.kt           ← 테스트 가게·메뉴·계정 정보
```

### 문제점별 개선 내용

| 문제 | 개선 |
|---|---|
| ① 원인 모를 에러 | `Ui.waitFor()`가 요소를 못 찾으면 "어느 화면, 어떤 요소"인지 담은 메시지로 실패 |
| ② 고정 시간 대기 | `Thread.sleep` 제거. 결제 처리 화면이 사라지고 주문 현황이 뜰 때까지 조건 기반으로 대기. 타임아웃은 `Timeouts`에 모아 CI에서 배율로 조정 |
| ③ 일시적 상태 | 주문 직후 허용되는 상태 집합(접수 대기, 접수 완료)으로 검증. 자동 접수를 꺼 둔 테스트 가게 사용 |
| ④ 문구 기반 셀렉터 | resource-id 기반 셀렉터로 변경. 목록은 스크롤하며 정확한 이름으로 검색 |
| ⑤ 약한 검증 | 주문번호, 가게명, 메뉴명, 결제금액, 상태를 각각 검증 |
| ⑥ 사전조건·데이터 | 테스트 전 API로 로그인, 배송지, 빈 장바구니, 가게 영업 상태를 세팅. 테스트 결제수단 명시. 테스트 후 주문 취소. 앱 실행 직후 알려진 팝업 처리 |
| ⑦ 구조 | 화면별 Page Object로 분리. 테스트 함수명을 검증 내용으로 변경 |
| ⑧ 실패 정보 | `FailureCaptureRule`이 실패 시 스크린샷과 UI 계층 덤프 저장 |

### 가정

- 앱 패키지명, resource-id, 테스트용 API는 예시입니다. 실제 적용 시 앱의 값으로 교체합니다.
- 테스트 계정·테스트 가게·테스트 결제수단이 준비된 테스트 환경을 전제로 합니다.

## 3. CI에서 간헐적으로 실패할 때 원인 추적 순서

1. **실패 패턴부터 확인합니다.**
   최근 실행 이력에서 실패율, 실패한 기기·OS, 시간대, 병렬 실행 여부를 봅니다. 특정 기기나 시간대에만 몰려 있으면 환경 문제일 가능성이 큽니다. 같은 커밋에서 성공과 실패가 섞여 있으면 Flaky로 판단하고 격리 여부를 정합니다.

2. **어느 단계에서 실패했는지 특정합니다.**
   실패 메시지(어떤 화면의 어떤 요소를 못 찾았는지), 스크린샷, UI 덤프, logcat을 확인합니다. 원본 코드처럼 NPE만 남는 경우에는 이 단계가 불가능하므로, 리팩토링에서 실패 메시지와 증거 저장을 먼저 넣었습니다.

3. **원인 유형을 분류합니다.**

   | 유형 | 확인 방법 | 이 테스트에서의 예 |
   |---|---|---|
   | 대기·타이밍 | 실패 시점 스크린샷에 로딩 중 화면이 있는지 | 결제 처리가 5초를 넘김 |
   | 예외 화면 | 스크린샷에 팝업·권한 요청이 있는지 | 이벤트 팝업이 결제 버튼을 가림 |
   | 셀렉터 | UI 덤프에서 같은 문구 요소가 여러 개인지 | "결제"가 결제수단 영역에 먼저 매칭 |
   | 테스트 데이터·상태 | 테스트 가게 영업 상태, 장바구니 잔여 상품 | 이전 테스트의 장바구니가 남아 있음 |
   | 상태 변화 | 주문 상태가 예상보다 빨리 바뀌었는지 | "접수 대기"가 곧바로 "접수 완료"로 변경 |
   | 환경 | 에뮬레이터 성능, 네트워크, 테스트 서버 장애 | CI 에뮬레이터가 로컬보다 느림 |
   | 실제 결함 | 같은 조건에서 수동으로도 재현되는지 | 결제 완료 후 간헐적으로 주문 현황이 안 뜸 |

4. **재현합니다.**
   같은 기기 조건(CI와 같은 에뮬레이터 이미지, 애니메이션 비활성화 여부)에서 해당 테스트만 반복 실행합니다. 의심되는 조건(느린 네트워크, 팝업 노출 계정)을 일부러 만들어 실패율이 올라가는지 봅니다.

5. **원인을 고치고 재발을 막습니다.**
   실제 결함이면 버그로 등록합니다. 테스트 문제면 고친 뒤 연속 N회 통과를 확인하고 격리를 해제합니다. 같은 유형이 반복되면(예: 팝업) 공통 처리로 옮겨 다른 테스트에도 적용합니다.

Flaky를 "테스트가 불안정하다"로만 보지 않고, 실제 결함 가능성(예: 결제 후 화면 전환이 간헐적으로 실패)을 3단계에서 함께 확인하는 것이 중요하다고 봅니다.
