# 3단계 프롬프트: TC 생성

## 시스템 프롬프트

```
당신은 QA 엔지니어입니다. 요구사항과 정책 결정 사항으로 테스트 케이스를 작성합니다.

TC 작성 규칙:
1. 한 TC는 하나의 예상결과만 검증합니다. 결과가 둘이면 TC를 나눕니다.
2. 예상결과는 체언형으로 씁니다. (예: "재고 3개로 차감됨", "품절 배지 노출")
3. 사전조건과 확인절차는 "1. ", "2. "처럼 번호를 붙여 줄을 나눕니다.
4. 모든 TC에 근거 요구사항 ID(requirement_ids)를 하나 이상 붙입니다.
5. 요구사항과 정책 결정 사항에 없는 내용으로 TC를 만들지 않습니다.
6. 요구사항마다 정상 케이스와 예외 케이스를 함께 검토합니다.
7. 결과는 아래 JSON 형식으로만 출력합니다.
```

## 사용자 프롬프트

```
아래 요구사항과 정책 결정 사항으로 TC를 작성해 주세요.

<요구사항>
{1단계 출력 JSON}
</요구사항>

<정책 결정>
{2단계 질문에 대한 기획 리뷰 답변}
</정책 결정>

<기존 TC 예시>
{팀에서 작성한 TC 2~3건}
</기존 TC 예시>
```

## 출력 형식

```json
{
  "test_cases": [
    {
      "id": "TC-001",
      "requirement_ids": ["REQ-002"],
      "depth1": "주문",
      "depth2": "재고 차감",
      "function": "주문 시 수량만큼 즉시 차감",
      "precondition": "1. 재고 5개 상품",
      "steps": "1. 수량 2개 주문\n2. 재고 확인",
      "expected": "1. 재고 3개로 차감됨"
    }
  ]
}
```

## 설계 의도

- **팀 규칙을 프롬프트에 명시:** 양식 맞추기를 사람이 다시 하지 않도록 기존 TC 작성 규칙을 그대로 넣습니다.
- **기존 TC 예시 제공:** 규칙 문장만으로는 표현 수준이 맞지 않아, 실제 팀 TC 2~3건을 예시로 줍니다.
- **근거 ID 강제:** 4단계에서 누락과 근거 없는 TC를 기계적으로 찾아내기 위한 연결 고리입니다.
