# 4단계: AI 출력 검증

4단계는 **규칙 검사**와 **내용 검토 프롬프트** 두 부분으로 나뉩니다.

## 4-1. 규칙 검사 (코드로 처리)

규칙으로 판정할 수 있는 항목은 AI에게 맡기지 않습니다.

| 검사 | 판정 기준 | 결과 |
|---|---|---|
| 요구사항 누락 | 1단계의 모든 요구사항 ID가 TC의 requirement_ids에 1회 이상 등장 | 빠진 ID 목록 → 해당 요구사항만 3단계 재실행 |
| 근거 없는 TC | TC의 requirement_ids가 모두 1단계 목록에 존재 | 없는 ID를 가진 TC → "검토 필요"로 분리 |
| 예상결과 개수 | expected에 번호 항목이 1개 | 2개 이상이면 분리 요청 |
| 필수 항목 | precondition, steps, expected가 비어 있지 않음 | 빈 항목 표시 |
| 체언형 | expected가 "~됨", "~노출", "~표시" 등으로 끝남 | 아니면 표현 수정 요청 |

## 4-2. 내용 검토 프롬프트

규칙 검사를 통과한 TC만 대상으로, 요구사항 원문과 내용이 맞는지 확인합니다.

### 시스템 프롬프트

```
당신은 다른 사람이 작성한 TC를 리뷰하는 시니어 QA 엔지니어입니다.
각 TC가 연결된 요구사항의 원문과 일치하는지 확인합니다.

확인 항목:
1. 예상결과가 요구사항 원문과 다른 값을 기대하고 있지 않은가
2. 사전조건이 요구사항의 조건을 제대로 만들고 있는가
3. 요구사항이 말하지 않은 내용을 예상결과로 기대하고 있지 않은가

규칙:
- 문제가 없는 TC는 출력하지 않습니다.
- 문제가 있으면 근거가 되는 요구사항 원문을 인용해 이유를 씁니다.
- TC를 직접 고치지 않고 수정 제안만 합니다.
- 결과는 아래 JSON 형식으로만 출력합니다.
```

### 사용자 프롬프트

```
<요구사항>
{1단계 출력 JSON}
</요구사항>

<TC>
{규칙 검사를 통과한 3단계 출력 JSON}
</TC>
```

### 출력 형식

```json
{
  "issues": [
    {
      "tc_id": "TC-007",
      "requirement_id": "REQ-004",
      "problem": "요구사항은 취소 시 즉시 복구인데 예상결과가 '다음 날 복구됨'으로 되어 있음",
      "source_quote": "주문 취소 (결제 완료 후) | 차감된 재고 즉시 복구",
      "suggestion": "예상결과를 '재고 즉시 복구됨'으로 수정"
    }
  ]
}
```

## 설계 의도

- **규칙 먼저, AI는 나중:** AI가 AI 결과를 검토하면 같은 실수를 반복하거나 문제없는 것을 문제로 볼 수 있습니다. 누락·근거·양식처럼 정답이 정해진 검사는 코드로 처리해 판정을 흔들리지 않게 합니다.
- **고치지 않고 제안만:** 검토 단계에서 AI가 TC를 직접 고치면 무엇이 바뀌었는지 추적하기 어렵습니다. 수정은 사람이 채택합니다.
- **원문 인용 필수:** 지적의 근거를 사람이 바로 확인할 수 있게 합니다.
